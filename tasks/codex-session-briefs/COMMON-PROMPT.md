# 任務

Kio の評価用 fixture コーパスのうち、**ユースケース `NN` (`pNN`) の担当分だけ**を生成します。

このコーパスは既に骨格が確定しています。決めてよいのは **中身の realism だけ**です。

| 決定済み (変更禁止) | あなたが作る (realism) |
|---|---|
| フォルダ構成・パス | 本文・文章・語り口 |
| 拡張子・形式・件数 | **filler のファイル名** (§絶対規則 3) |
| `★正解`/`△distractor` のファイル名 | 図表の見た目・レイアウト |
| ページ / スライド数 | コードの中身・データの中身 |
| 埋め込む事実 (fact) の値と文言 | 事実の周囲の自然な文脈 |
| 正解 / distractor / filler の役割 | 業務としての一貫性 |

**ゴール**: 生成物が「実在するその職種の人の PC フォルダ」に見えること。
合成テストデータに見えてはいけません。

# 絶対規則 — 1 つでも破ったら成果物は破棄されます

1. **`.kio` を作らない・触らない・書かない。**
   Kio の内部 (objects / index / sqlite / CAS / それ相当の索引ファイル) を自分で作ることは
   全面禁止です。作るのは **普通のファイルとフォルダだけ**。

2. **OCR・Office→PDF 変換・embedding・索引化を自分で実行しない。**
   これらは後段で **実際の Kio パイプライン**
   (`kio init` → `kio index --approve --online`) だけが行います。
   あなたはその入力となる素のファイルを置くだけです。

3. **骨格を変えない。ただしファイル名だけは例外がある。**

   **確定契約 (変更禁止)**: leaf フォルダのパス・**各 leaf のファイル件数**・拡張子・形式 /
   subtype・言語・レーン・役割・ページ / スライド数。**追加・削除・移動・形式変更をしない。**

   **ファイル名は 2 種類ある**:

   | 種類 | 例 | 扱い |
   |---|---|---|
   | **固定** — 役割が `★正解` / `△distractor` | `latency-review.docx` | **1 文字も変えない**。§4 の契約が参照している |
   | **プレースホルダ** — `-001` の連番、`-pNN` の接尾辞 | `worklog-001.md` / `budget-sheet-p01.xlsx` | **あなたが realistic な名前に付け替える** |

   プレースホルダ名は骨格を機械生成したときの仮の名前です。**そのまま使うと成果物が合成
   データに見えます** — 実在する人の PC に `utility-021.rs` や `worklog-001.md` は並びません。
   連番でも `-pNN` でもない名前 (`context-overview.md` 等) は、すでに自然なのでそのまま使って
   構いません。

4. **事実 (fact) の契約を守る。**
   ブリーフ §4 に「埋め込む事実」が実文言で指定されています。
   その値・表現をそのまま使い、**あなたの担当範囲では 1 回だけ**出現させます。
   distractor には **近いが異なる値**を入れ、正解の事実は絶対に含めません。

   事実の文言は**すでに確定しており、あなたが考案するものではありません**。勝手に言い換えたり
   値を変えたりしないでください。「コーパス全体で 1 回のみ」は全セッション完了後に一括検証
   しますが、そのためには**指定文言をそのまま使うこと**が前提です。

   併せて、**担当ペルソナ以外の事実値を偶然書いてしまわない**よう注意してください。
   他ペルソナの製品名・数値をあなたの本文に登場させないでください。

5. **テストのためだけの不自然な内容を作らない。**
   「ここを通すため」の作為的なファイル・文言は禁止。すべて、その職種の人が
   実際に持つ / 書く体裁にしてください。

6. **text 系は strict UTF-8・BOM なし・NUL バイトなし。**
   エンコーディングが混ざると索引から静かに落ちます。

7. **ファイルは指定された leaf フォルダの直下にのみ置く。**
   中間ディレクトリに勝手にファイルを置かない (Kio の索引はサブフォルダを再帰しません)。

8. **1 ファイル 5 MiB 以下。PDF / PPTX は 20 ページ・20 スライド以下。**

9. **事実・クエリ・ソース ID・ファイル名をメタデータに書かない。**
   Office のプロパティ / alt text / ノート欄 / ChartML、画像の EXIF / XMP / PNG text。

# 進め方

### Step 1 — 読む
ブリーフ全文と、そこで参照されているソース資産を読む。担当ファイル数・形式分布・
正解クエリを把握する。

### Step 1.5 — プレースホルダ名を realistic な名前に置き換える

世界観 (Step 2) を決めた**あと**、プレースホルダ名を実務的な名前へ付け替えます。

**満たすこと**

- **中身を表す名前にする。** カテゴリ名 (`utility` / `worklog` / `record`) ではなく、
  そのファイルが実際に何であるかを書く。
- **決めた世界観の語彙を使う。** 製品名・案件名・チーム名・機能名が名前に現れてよい。
- **命名規則を生態系に合わせる。** Python は `snake_case.py`、Rust は `snake_case.rs`、
  TypeScript は `kebab-case.ts` が自然。Markdown のメモは日付入り (`2026-07-03-retro.md`) も可。
- **自然にばらつかせる。** 全部が同じ語形だと機械生成に見える。略語・日付・担当者イニシャル・
  版番号などが混ざるのが実際のフォルダ。
- **ペルソナ内で一意にする。** 別 leaf なら同名でもよいが、紛らわしいものは避ける。

**やってはいけないこと**

- 連番を機械的に振り直すだけ (`utility-021.rs` → `helper-021.rs` は無意味)
- `-pNN` を残す (`budget-sheet-p01.xlsx` は実在しない名前)
- 役割が `★正解` / `△distractor` のファイルを改名する
- 拡張子・形式・件数を変える

**例** (決済プロダクトの開発者の場合)

| プレースホルダ | 付け替え後 |
|---|---|
| `utility-021.rs` | `posting_link.rs` |
| `worklog-001.md` | `orchid-ledger-設計確認メモ.md` |
| `activity-014.jsonl` | `settlement-replay-2026-07.jsonl` |
| `budget-sheet-p01.xlsx` | `Q3-インフラ費用見積.xlsx` |

### Step 2 — 世界観を決める
`pNN` の職種として、**一貫した業務世界**を 1 つ決める。
製品名・案件名・チーム名・期間・主要な数値を固定し、**全ファイルで共有**させる。
(例: 同じ製品の設計書・議事録・コード・障害記録・スライドが互いに参照し合う)

これが realism の核心です。ファイルが互いに無関係だと合成データに見えます。

### Step 3 — 形式ごとに生成
ブリーフ §3 の割当に従います。

| 対象 | 使うもの |
|---|---|
| DOCX | **Word プラグイン** — 見出し・表・ヘッダ/フッタを持つ実務文書 |
| PPTX | **PowerPoint プラグイン** — 図表画像を埋め込んだ実務スライド |
| XLSX | **Excel プラグイン** — 実務の表 (Kio は索引しない realism 専用) |
| PNG / JPEG | **画像生成・レンダラ** — 数値/軸/凡例は**画素に描画**する |
| PDF (テキスト層あり) | TeX を realistic に書き換えてビルド |
| PDF (スキャン) | TeX → PDF → `pdftoppm -r 200 -png` → 画像を PDF に再束ね。**テキスト層ゼロ**にする |
| md / code / log / json / yaml / csv / ipynb / html / eml | 直接記述 |

**図表の注意**: 事実を持つ図は必ずレンダリング (matplotlib / PIL / TeX→PNG) で
**文字を画素に描く**。装飾目的で拡散生成画像を使う場合は **文字を一切載せない**。

**hard1 (スキャン PDF) の再束ね**: `img2pdf` があればそれを使ってください。無い環境では
Pillow で同等の結果が得られます (このリポジトリの環境で検証済み — `pdftotext` 出力が空になる)。

```python
from PIL import Image
pages = [Image.open(p).convert("RGB") for p in sorted(png_paths)]
pages[0].save(out_pdf, "PDF", resolution=200, save_all=True, append_images=pages[1:])
```

どちらの方法でも、最後に `pdftotext <out.pdf> -` の出力が (空白除去後) **空**であることを
必ず確認してください。

### Step 4 — 自己検査
ブリーフ §6 のチェックリストを**すべて**満たすまで終了しない。特に:
- 生成ファイル数がブリーフの数値と完全一致しているか
- **プレースホルダ名 (`-001` 連番 / `-pNN`) が 1 つも残っていないか**
- **`★正解` / `△distractor` のファイル名を変えていないか**
- `.kio` を 1 つも作っていないか
- `home/` のファイルが全て leaf 直下か
- 事実がコーパス内 1 回だけか、distractor に漏れていないか
- hard1 がある場合、最終 PDF の `pdftotext` 出力が (空白除去後) 空か

# よくある失敗 (やってはいけないこと)

- ❌ `.kio` フォルダを作る / Kio の索引ファイルを自分で書く
- ❌ 「索引した」「OCR した」「embedding した」と称して自分で処理する
- ❌ ファイルを追加・削除・移動したり、形式・件数を変えて骨格を崩す
- ❌ 事実の値を自分で決め直す / 言い換えてしまう
- ❌ 自分に割り当てられた `pNN` 以外の persona のフォルダを作る / 触る
- ❌ 合成っぽい連番ファイル名や "Synthetic ___" のようなプレースホルダ本文を残す
- ❌ プレースホルダ名 (`worklog-001.md` / `budget-sheet-p01.xlsx`) をそのまま提出する
- ❌ 逆に `★正解` / `△distractor` のファイル名を「自然でないから」と改名する
