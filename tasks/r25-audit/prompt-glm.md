# Kio 実装監査 R25 (GLM 系統) — 直近変更面の問題洗い出しと次作業の提案

あなたは Kio (local-first knowledge archive、Rust 実装) の**実装監査**を単独で行う。
他系統の報告は与えられていない。自分の読解だけで判断せよ。

監査対象は同ディレクトリの `target.md` **のみ**である。ここに無いファイルの内容を
推測して指摘を作ってはならない。`target.md` の抜粋には出典の行範囲が明記されている。
**抜粋の切れ目を連続したコードとして読むな。**

## 0. 読了証明 (報告書の冒頭に必ず置く)

```
READ-PROOF
1. target.md の総行数: <数値>
2. target.md の最終 2 行を verbatim:
   <ここに引用>
```

## 1. 背景

Kio の横断検索は最近、次の 2 段階で変更された。

1. **scatter-gather → replication**: 各フォルダの `.kio` が持つ per-scope SQLite index を
   device 単位の replica (`aggregator.sqlite`) へ複製し、BM25 を単一コーパス上で計算する。
   従来は per-scope に分かれた索引ごとに BM25 を計算しており、同じ語でも scope の大きさで
   スコアが変わっていた。
2. **読み手による検知 → 書き手による write-through**: 当初は検索時に `index_generation`
   スタンプを比較して差分 scope を射影し直していた。しかし索引を in-place に書き換える経路の
   一部が `index_generation` を回転させていなかったため、正本を書いた処理が同じ処理の中で
   replica にも書く方式へ変更した。

`target.md` にはこの 2 変更の設計書、新規モジュールの全文、規範文書の該当節、
および各 write-through hook の実装抜粋が入っている。

## 2. 求めるもの

### Part A — 問題の洗い出し

`target.md` の範囲で、実装・設計・規範のいずれかに**実在する**問題を挙げよ。

挙げてよいもの: 実装の欠陥、規範と実装の乖離、未完了の穴、競合・順序の問題、
リソースやトランザクションの扱いの誤り、秘匿情報の扱いの穴。

挙げてはならないもの: 資料 7 (backlog §7) に**すでに記載済みの項目の再掲**
(ただし記載が事実として誤っている場合はその差分を明示して挙げてよい)、
根拠を引用できない推測、スタイルの好み。

1 件ごとにこの形で書け。

```
### [G<連番>] <一文の要約>
- 重大度: fatal | major | minor
- 対象: <資料番号と行番号>
- 根拠: <target.md からの verbatim 引用。行番号を添えること>
- 何が起きるか: <どの入力・どの順序で何が壊れるか。「〜かもしれない」は書くな>
```

**重大度**: `fatal` = データ損失・秘匿漏洩・正しい入力で必ず壊れる /
`major` = 特定条件下で誤った結果・回復に手作業 / `minor` = 実害限定的。

### Part B — 次の作業の計画

Part A を踏まえ、次に着手すべき作業を **4〜6 項目**、優先順位付きで提案せよ。

```
| 順位 | 作業 | なぜこの順位か (先にやらないと何が起きるか) | 概算規模 |
|---|---|---|---|
```

規模は「1 日未満 / 数日 / 1 週間以上」の 3 段階。

## 3. 判定

最終行に次の 3 語のいずれか 1 つだけを書け。

```
判定: 合格
判定: 条件付き合格
判定: 不合格
```

`合格` = このまま次の機能開発へ進んでよい /
`条件付き合格` = 先に潰すべき指摘があるが設計の作り直しは不要 /
`不合格` = 基盤に作り直しを要する欠陥がある。

## 4. 出力の制約 (厳守)

- **報告書全体を 250 行以内に収めよ。** 超過が見込まれるなら指摘件数を絞り、
  重大度の高いものだけを残せ。長さより完結性を優先する。
- 監査報告書**のみ**を出力せよ。作業ログ、思考過程、作業状態は出力するな。
- 日本語で書け。
- 構成は `READ-PROOF` → `## Part A` → `## Part B` → `判定: <3語のいずれか>` に固定する。
