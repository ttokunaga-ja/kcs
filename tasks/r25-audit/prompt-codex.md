## 3. Part A の要件 — 問題の洗い出し

### 3.1 何を「問題」として挙げてよいか

- **実装の欠陥**: 誤った条件、抜けた経路、競合、リソース枯渇、誤ったエラー処理。
- **仕様との乖離**: `docs/` の規範が要求することを実装がしていない、またはその逆。
- **未完了の穴**: 「後で」と書かれたまま放置され、実害が出る状態にあるもの。
- **構造的な問題**: 保守不能な規模・重複・責務の混線など、**具体的な害を示せる場合に限り**。

### 3.2 何を挙げてはならないか

- `tasks/step4b-backlog.md` に**すでに記載済みの項目をそのまま再掲すること**。
  ただし「backlog の記載が事実として誤っている」「重大度の評価が誤っている」
  「記載されているが実際にはもっと広い範囲に影響する」場合は、**その差分を明示した上で挙げてよい**。
- コードを読まずに推測した問題。
- スタイル・命名の好み。

### 3.3 指摘の書式 (1 件ごとにこの形)

```
### [A<連番>] <一文の要約>

- 重大度: fatal | major | minor
- 対象: <path>:<行番号> (複数可)
- 根拠: <原文の引用。引用は必ず verbatim。行番号を添えること>
- 何が起きるか: <具体的な失敗の筋道。「〜かもしれない」ではなく、
  どの入力・どの順序で、何が壊れるかを書く>
- 再現手順: <可能なら CLI 操作列。不可能なら「静的指摘」と明記し、
  なぜ実行なしで断定できるかを書く>
- backlog との関係: 新規 | 既知だが評価が誤り (差分を明記) | 既知の範囲外への波及
```

**重大度の定義**:
- `fatal` = データ損失、秘匿情報の漏洩、または正しい入力で必ず壊れる。
- `major` = 特定条件下で誤った結果を返す、または回復に手作業を要する。
- `minor` = 実害は限定的だが、放置すると悪化する。

**根拠のない断定は書くな。** 引用できない主張は挙げないこと。

## 4. Part B の要件 — 次の作業の計画

Part A の結果と、backlog に残る未完了項目の両方を踏まえて、**次に着手すべき作業**を提案せよ。

```
### 計画

| 順位 | 作業 | なぜこの順位か | 概算規模 | 前提・リスク |
|---|---|---|---|---|
```

- **5〜9 項目**に絞れ。網羅列挙は求めていない。
- 「なぜこの順位か」には、**先にやらないと何が起きるか**を書け。
- 少なくとも 1 項目は「やらない方がよい / 後回しでよい」ものを挙げ、その理由を書け。
- 規模は「1 日未満 / 数日 / 1 週間以上」の 3 段階でよい。

## 5. 判定

報告書の Part A と Part B の後、**最終行**に次の 3 語のいずれか 1 つだけを書け。

```
判定: 合格
判定: 条件付き合格
判定: 不合格
```

- `合格` = 現状のまま次の機能開発へ進んでよい。
- `条件付き合格` = 先に潰すべき指摘があるが、設計の作り直しは不要。
- `不合格` = 設計または実装の基盤に、作り直しを要する欠陥がある。
