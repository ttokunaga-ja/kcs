# 1. 3 つのクラスと、各レーンの到達範囲

| クラス | 中身 | FTS | vector | rerank |
|---|---|---|---|---|
| **A** | born-digital のテキスト | ✓ | ✓ | ✓ |
| **B** | **OCR が文字に起こしたもの** | ✓ | ✓ | ✓ |
| **C** | **OCR が「画像として残す」と判断したもの** | ✗ | ✓ | 対象外 (§4) |

B と C の線引きは **OCR 側の判断**である。文字に起こせたものは本物のテキストなので
全文検索に入れる。図表・写真のように起こしても意味を成さないものは、
ベクトルでだけ引ける。

**vector の列が 3 クラスとも ✓ なのは、既にそうなっているからである。**
07 §5.3 の埋め込みは**単一マルチモーダル空間**で、画像オブジェクトも同じ空間に入る
(`local_embedding` の `IMAGE_OBJECT_CAPABILITY`)。別空間を作る必要はない —
**作ってはいけない。**03 §7 の互換ゲートは `tool_profile_hash` しか見ないので、
同じ profile で 2 つの空間を持つと区別がつかない。

# 2. クラス C は実際にはどういう文書か

`eval/fixtures/normalized-corpus/` の 1,015 件のうち **90 件が画像参照を持ち、
36 件は画像を除くと本文 200 字未満**。実物:

```
## Run 001 exported signal distribution
![img-0.jpeg](img-0.jpeg)

# Study Alpha dilution response
![img-0.jpeg](img-0.jpeg)
Normalized response (%)

# 2026年Q1 締め作業ルーム — 当番カバレッジ
財務経理部・Orion ERP close room
![img-0.jpeg](img-0.jpeg)

# Rendered citation network
Afterlives of Judgment · Keller-Roth correspondence reading set
![img-0.jpeg](img-0.jpeg)
```

中身はグラフ、実験の応答曲線、配置図、引用ネットワーク、装置写真。

**設計上いちばん効く事実: どれも無テキストではない。**全部に見出しがあり、
多くにキャプションか軸ラベルがある。`Study Alpha dilution response`、
`財務経理部・Orion ERP close room`、`Afterlives of Judgment` は**本物の語彙情報**で、
**人が figure を探すときの手がかりはここにある。**

そして kio は既にこれを **2 行に分けている** — 見出し + キャプションの
**chunk 行** (FTS + vector) と、**画像オブジェクト行** (vector のみ)。
`result_type` が区別し、`row_id` が互いに潰れないようにしている
(`kio-cli/src/main.rs` の `ResultPayload`)。**クラス C の話は画像オブジェクト行のこと**で、
見出しとキャプションは chunk 行として今も全文検索に入っている。

# 3. 訂正 — qb22 は根拠にならない

初版は qb22 (`citation-network.jpeg`、3 モデルとも 7 位 → 37 位) を
「reranker が画像を壊した」例として使った。実物を見て崩れた:

- **このフィクスチャに `img-0.jpeg` は 1 件も存在しない。**1,015 件すべて `.md` で、
  画像参照は実体の無いファイルを指している
- したがって qb22 は**どの手法でも正解できない。**答えは画素の中にあり、
  その画素がコーパスに無い
- baseline の 7 位は見出しとキャプションの語に意味的に当たっただけで、
  **reranker がそれを落としたのは正しい判断である。**テキストは実際に
  質問 (「Arendt ノードへの流入引用数」) に答えていない

**したがって初版の「棄権で +0.0417」は、偽陽性を拾い直していただけである。**

棄権という規則自体 (テキストの無い候補をテキスト cross-encoder が動かすべきでない)
は誤りだと示されたわけではない。**示されたのは、それを支える証拠が無かったこと。**
そして §4 の方針を採ると、画像行はそもそも既定のランキングに入らないので、
**棄権の出番はほぼ無くなる。**

# 4. 方針 — 既定では出さない。明示的な画像検索でだけ出す

**確定 [2026-08-11]。**検討した 3 案:

| 案 | 判断 |
|---|---|
| **1. 既定のランキングに入れる** | ハイブリッドでは既にそう動く。全文のみの検索で出ないのは**欠陥ではなく正しい** — テキストしか手がかりの無い検索に画像を評価する手段は無い |
| **2. 既定では出さず、明示的な画像検索でだけ出す** | **採用** |
| **3. Embedding スコアをそのままランキングに使う** | **不採用**。RRF が**スコアではなく順位**を融合しているのは、レーン間のスコアが比較不能だからである。1 クラスだけ生スコアを持ち込めば比較不能性が戻る。語レーンで等重み融合が高精度レーンを引きずり下ろしたのと同じ構図で、尺度が違うぶん質が悪い |

案 2 を採る理由は §2 の実物にある。**figure を探す人の手がかりは見出しとキャプション**で、
それは chunk 行が持っていて全文でも当たる。`related_images[]` が chunk から figure へ
繋がっているので、**見つける入口は既にある。**画像そのものを列挙したいときだけ
opt-in する、という切り分けが文書の実際の構造と合っている。

## 4.1 これは何を意味するか

- 画像オブジェクト行は**既定の検索結果に出ない**
- 明示的な画像検索 (引数側のオプション) のときだけランキングに入る
- そのモードでの順位付けは vector の順位による。**生スコアは使わない** (案 3 の理由)
- reranker は画像行を**受け取らない**。テキスト cross-encoder に渡す意味が無い

# 5. まだ検証していないこと

- **この方針は測定ではなく、文書構造からの判断である。**§2 の実物を見て決めた
- **現行フィクスチャでは案 1 と 2 の差を測れない。**画像オブジェクトが 1 件も無い
  (§3)。測るには**実画像を含むフィクスチャ**が要る —
  `eval/register_fixture.py` が作る本来の fixture (元の `.pdf` / `.png` を持つ) が
  それに当たるはず

  知っているのは Markdownize Adapter だけで、いま出力していない。
  信号は派生インデックスに置く — `chunk_hash` に入れると、再 OCR で
  07 §9 が同じ文書を別物と見なす
- キャプションを FTS に入れるかは、**§2 の時点で既に入っている** (chunk 行として)。
  初版が「C は FTS ✗」と書いたのは画像オブジェクト行の話で、
  文書全体の話ではない
