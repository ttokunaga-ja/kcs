# 語レーンの効果測定 — 事前登録と結果

`tasks/japanese-word-lane-design.md` で設計し実装した word lane (既定 off) を、
**on にする根拠があるか / 消すべきか** を決めるための測定。

**予測は測定より先に書く。**下の §3 は 1 回も走らせる前に書かれており、
走らせた後で書き換えていない。当たったか外れたかは §4 に足す。

---

# 1. なぜ新しいクエリ集合が要るのか

リポジトリ内の既存ゴールデンクエリ 98 問を数えた結果:

| | |
|---|---|
| length rule (05 §1.3、3 scalar 未満を捨てる) が漢字の内容語を落としているクエリ | **92 / 98 (94%)** |
| 落とされた Han run の総数 | **315** (`資料`×10, `万円`×7, `検索`×6, `廃止`×5) |
| 長さだけで生き残る純粋な文法 run | **109** (`だった`×20, `はいくつか`×6, `はいつか`×5) |
| それでも Recall@10 | golden 50 = **1.000** / crossscope 16 = **1.000** / qhard 8/8 |

**倒錯は 94% のクエリで現に起きているのに、一度も recall を落としていない。**
理由はクエリの長さで、90 問の**最短が 14 文字・中央値 29 文字・12 文字以下は 0 問**。
どれも記述文なので、捨てられた内容語の外側に必ず別の識別語が残っている。

語レーンは短いクエリのために作った。**その場合を測る問題が 1 問もない。**

# 2. 器 — `eval/golden-queries-short.jsonl`

自分の機能に有利な問題を書かないための拘束を先に決めた:

1. **M3-1 anchor の全 24 section に 1 問ずつ。**どれを載せるか選べないので、
   有利な事例だけを拾うことが構造的にできない
2. **12 文字以下。**既存 98 問の最短が 14 文字なので、集合として重ならない
3. **語彙は当該 anchor の `title` / `heading` / `facts` に verbatim で現れるものだけ。**
   機械検査済み (この規則に 2 問違反していたので、走らせる前に直した)
4. **形態素解析器の挙動を見ずに書く。**文書を思い浮かべて打つ言葉を書く
5. **走らせる前に凍結する**

コーパスには一切手を入れていない (crossscope 増補と同じ方針)。
Rust `kio-eval --golden` が既にあるのでランナー改修も不要。M3-2/M3-3 の
`HISTORY_QUERY_COUNT` 契約は M3-1 のみの実行には当たらない。

# 3. 事前予測 (走らせる前に記載)

24 問に length rule を当てた結果 (トリガム側だけの計算、語レーン不関与):

- **pure-short は 0 / 24。**どの問にも 3 文字以上の生存 unit がある
- **内容語が捨てられる問は 18 / 24**
- 生存 unit に `の精度` `の目標` `の定数` `の係数` `の推奨` `の同一性` が並ぶ。
  script run 境界は字種でしか切らないので、**助詞が内容語に溶接されたまま
  1 つの unit になっている。**設計文書が書いた倒錯より一段悪い形

**予測: 語レーン off でも短問集合は天井に近い (Recall@10 >= 0.9)。したがって
レーンによる改善は +0.1 以下、おそらく 0。**

根拠は anchor の語彙的な特異性で、M3-1 の 12 文書はすべて固有名詞
(`Osprey` `Komodo` `RRF` `MMR` `HNSW` `Falcon` `Kestrel` `ベロシティ`
`マネージド`) を持ち、**length rule はカタカナ語も ASCII 語も捨てない。**
内容語の漢字が落ちても、固有名詞が単独で文書を一意に決めてしまう。

対照群は内容語が 1 つも落ちない 6 問 (`ハイブリッドの p99`,
`マイルストーンとベータ`, `スプリントのベロシティ`, `Komodo の QPS`,
`トークンの TTL`, `chunk の同一性`)。ここが動いたら、それは改善ではなく事故。

**この予測が当たった場合、結論はレーンではなく器についてのものになる** —
合成コーパスは anchor が語彙的に目立ちすぎて、どんなクエリを書いても
この問題を測れない。その場合の次の一手は合成コーパスの改良ではなく、
実文書コーパス (`tasks/dogfood-realistic-corpus-investigation.md`) への移行。

**反証条件: off が 0.9 を明確に下回れば、レーンには伸びしろがあり、
差分をそのまま効果として読める。**

# 4. 結果 [2026-08-10]

同一機・同一 session。コーパスは byte 同一のものを 2 つ生成し、それぞれのバイナリで
`replay_history` から作り直した (語レーンは索引時に列を作るので、索引を共有できない)。

## 4.1 短問集合 — 予測どおり、レーンは何もしなかった

| | Recall@10 | 内訳 | p95 |
|---|---|---|---|
| word-lane **off** | **0.9167** | 22 / 24 | 88.8ms |
| word-lane **on** | **0.9167** | 22 / 24 | 88.7ms |

**差は 0。落ちた 2 問も同一** (`Osprey の精度`, `Komodo の QPS`)。
§3 の予測「off でも >= 0.9、改善は 0」は当たった。

## 4.2 予測していなかったこと — 既存 50 問が**悪化**した

| | M3-1 | M3-2 | M3-3 | p95 (M3-1/2/3) |
|---|---|---|---|---|
| off | 1.000 | **1.000** | **1.000** | 89 / 88 / 88 ms |
| on | 1.000 | **0.938** | **0.938** | 98 / 103 / 124 ms |

**改善したクエリは 0 件。悪化したクエリが 2 件**、いずれも 1.00 → 0.00:

**(a) `chunk size was 512 tokens in the retrieval pipeline doc` (M3-2)**

英語クエリ。off では `rag-pipeline.md` が 3 位、`retrieval-pipeline.md` が 4 位に
入っていた。on では**両方とも top 10 から消え**、`memo-0009` `memo-0033`
`draft-0019` `draft-0027` `memo-0037` という filler 文書に置き換わった。

原因は品詞フィルタの出自。落とす品詞は IPADIC のもので、**IPADIC が機能語として
知っているのは日本語の機能語だけ**。`the` `in` `was` `of` は未知語として名詞に倒れ、
そのまま OR の腕になる。頻出語が腕になれば filler が上位に来る。
`build_word_match_expr` はクエリの字種を見ずに常に IPADIC を通しており、
**英語クエリでレーンが起動してはいけない**という判断がどこにも無い。

**(b) `廃止した旧フォーマット v0.1.0 の仕様書` (M3-3)**

日本語クエリ。こちらは字種で門前払いできない、より深い方。

off の結果は **3 件だけ、すべて `legacy-format-v0.md`** — トリグラムが完璧な精度で
答えていた。on では `legacy-format-v0.md` が **6 位まで落ち**、1〜5 位は
`deprecated-approach` `vendor-eval` `leaked-draft-pricing` `falcon-old-schema`
`kestrel-poc-metrics` — **`廃止` `旧` を含むだけの文書**が占めた。

原因は融合の重み。`merge_text_lanes` は `fuse_rrf` を `w_text: 1.0, w_vector: 1.0`
で再利用している (設計文書 §4.1「RRF の継ぎ目は既にある」)。**等重み RRF は、
精度の低いレーンに精度の高いレーンを引きずり下ろす権利を与える。**トリグラムが
3 件で当てているところに、語レーンが一般語で拾った 5 件が同じ重みで入る。

継ぎ目が既にあることを利点として数えたのは誤りだった。**空いている穴の形は、
そこに入れてよいものの形を意味しない。**

## 4.3 コスト (再掲・実測)

| | off | on |
|---|---|---|
| バイナリ | 16.0 MB | **74.6 MB** (埋め込み IPADIC) |
| 索引時間 (contract suite) | 82.93s | **123.84s** (+49%) |
| 検索 p95 (M3-3) | 88ms | **124ms** (+41%) |

なお schema 側 (`text_words` 列・`chunk_word_fts`・trigger 3 本) は
`#[cfg(feature = "word-lane")]` の中にある (`crates/kio-index/src/fts.rs:760`) ので、
**feature off のビルドは実行時コストを 1 つも払っていない。**

# 5. 判断

**レーンは席に値しない。実装を revert することを推奨する。**

- 作った目的 (短いクエリ) では**効果が測定上ゼロ**
- 目的外では**実測で悪化**する。しかも改善は 1 件も無い
- 悪化の (a) は字種ゲートで直せるが、(b) は融合の重み付けの問題で、
  **調整するための器が無い** — その器が無いことが §4.1 の結論そのものなので、循環する
- 仮に両方直しても、到達点は「変化なし」で、+49% と +58MB を正当化しない

設計文書の主張 (品詞は長さでは代替できない) 自体は**誤りだと示されたわけではない**。
示されたのは、**この合成コーパスでは真偽を問えない**ということ。anchor が
`Osprey` `Komodo` `RRF` `HNSW` のような固有名詞を必ず持ち、length rule は
カタカナも ASCII も落とさないので、漢字の内容語が落ちても文書が一意に決まってしまう。

したがって次に語レーンを再考するのは、**実文書コーパスに移った後**
(`tasks/dogfood-realistic-corpus-investigation.md`)。そこで短問の recall に
伸びしろが実測できたときに限る。実装は `57850f0` から復元できる。

`eval/golden-queries-short.jsonl` は**残す。**レーンとは独立に、
「12 文字以下のクエリ」というこれまで 1 問も無かった領域を 24 問で押さえており、
今回 off で 22/24 という基準線も取れている。

# 6. なぜ契約テストは 1 つも落ちなかったのか

レーンには契約テストが 4 本あり (`word_lane_contract.rs`)、**全部 green だった**。
実測で悪化していたのに落ちなかったのは、**4 本とも索引した文書が 1 件だけ**
だったから。

| test | 索引した文書 | 主張していたこと |
|---|---|---|
| `wl1_a_two_scalar_content_word_finds_its_document` | `keiyaku.md` のみ | 見つかる |
| `wl2_a_grammar_only_query_does_not_retrieve...` | `keiyaku.md` のみ | 見つからない |
| `wl3_the_trigram_lane_still_answers_identifier...` | `config.md` のみ | 見つかる |
| `wl4_a_document_both_lanes_find_is_returned_once` | `gijiroku.md` のみ | 融合が重複を出さない |

**このレーンの主張は順位についてのものだった。**第 2 レーンを RRF に融合する、
というのが全部である。**1 件しか無いコーパスには順位が無い。**とくに `wl4` は
「融合が文書を重複させない」を**文書 1 件**に対して主張していて、実測で起きた
「正解が 6 位に落ちる」は構造的に観測できない。

これは「機能が起動すること」を検証していて、**契約の観測量 (競合との順序) を
検証していなかった**ということ。実装の隣で書いたテストは、実装が動くことを
書き写しやすい。書くべきだったのは**差分テスト** — 同じコーパスに対して
feature on/off で走らせ、on が off を下回らないことを主張するもの。
それは結局 §4 でやったことで、そして落ちた。

**逆に、テストが問題ないと確認できたもの:**

- **`eval/golden-queries.jsonl` は実装に合わせて調整されていない。**`git log --follow`
  で**コミットは 1 つだけ** (`f33d68b`, 2026-07-03)。作られたのは Step 3 の契約テスト
  仕様と同じコミットで、**検索実装より前** (以後 `main.rs` に 23 コミット)。
  一度も編集されていない。事前登録されていたと言ってよい
- **escape 修正の `f3_*` テストは 1 文書でよい。**あの欠陥は「見つかる / 見つからない」の
  二値で、順位が関与しない。1 文書コーパスで `!results.is_empty()` + snippet の内容
  検査は、契約の観測量そのもの。**テストの層ではなく、欠陥の種類の問題である**

**繰越: step 2 の reranker は純粋に順位の変更なので、契約テストは構造的に
盲目になる。**eval ハーネスで on/off の差分を測ることを着手条件に含めること。
