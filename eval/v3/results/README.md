# V3 実測結果 — V3a (2026-07-28) / V3b・V8(a) (2026-08-01)

`tasks/local-adapter-plan.md` の **V3**「MRL 切り詰め (native 2048 → 768) が
検索品質をどれだけ落とすか」を GPU 実機で測った記録。**V3b まで完了し、V3 は決着した。**

> **結論 (2026-08-01): `dimensions` は 768 で確定。**
> 24 問 fixture の recall@10 は native 2048 が 0.5417、MRL 768 が **0.5833** で、
> **切り詰めても落ちていない** (むしろ +1 問)。2048 への移行は全再埋め込みと
> `chunk_vec` の DDL 改訂を要するのに、測った recall はより低い。
> → `tool_profile_hash` = `sha256:f9f610bb…439a` の**暫定扱いを解除**し、
> 恒久コーパスの埋め込み禁止も解ける。詳細は下記「判断」。

> **0.5417 / 0.5833 を Kio の検索品質と読まないこと。** `tasks/local-adapter-plan.md`
> の品質計器の表は同じ 24 問 fixture で Rust baseline の **0.9167** を挙げているが、
> **計器が違う**。`kio-eval benchmark baseline` は実際の `kio` バイナリを
> `kio --json search <query> --all-scopes` で回すので chunk 分割・hybrid・集約まで
> 通っている。`v3_mrl.py` は Kio を通さず **1 ファイル = 1 passage** (分割なし・
> 先頭 4000 文字) の素の cosine だけを見る。
>
> 粗いままにしてあるのは意図的で、**比べているのは同じベクトルの 2 つの幅**だから
> である。分割規則も入力構築も instruction も両側で相殺されるので、幅の効果だけが
> 残る。**絶対値には意味が無く、差だけが意味を持つ。** 0.5417 は 0.9167 からの
> 劣化ではない。

## コーパス

**このリポジトリ自身の Markdown 136 本** (`docs/` 12 + `tasks/` 118 + リポジトリ直下 6)。
`~/kio-baseline-corpus` はこの機械に無く、`docs/` だけでは 12 本で
`v3_mrl.py` の下限 (20 passages) に届かないため広げた。

計画書が言うとおり **測っているのは幅の効果であってコーパスの絶対性能ではない**。
サーバへ投げるのは 1 passage につき 1 回だけで、返った 2048 次元から 768 版を
導出して比べるので、chunk の切り方も入力構築も instruction も両側で相殺される。

```bash
# 収集はフラット化するだけ (1 ファイル = 1 passage)。commit 2e7a2ba で再現できる。
mkdir -p /tmp/v3-corpus
for f in $(find docs tasks -name '*.md') $(find . -maxdepth 1 -name '*.md'); do
  cp "$f" "/tmp/v3-corpus/$(echo "${f#./}" | tr / _)"
done

python3 eval/v3/v3_mrl.py --corpus /tmp/v3-corpus \
  --queries eval/golden-queries-fixture-b.jsonl --out v3-mrl.json
```

## V3a の判断 — V3b へ進んだ

判断表で `< 0.85` は「近傍が崩れている → 24 問 fixture での recall 実測 (V3b) へ」。
**曖昧帯 (0.85–0.95) も同じく V3b へ送られるので、V3b を回避できたのは
`≥ 0.95` の場合だけだった** — 0.8037 はそこから遠く、下記の補正を入れても届かない。

→ V3b を実施した (下記)。**その結果、近傍の入れ替わりは recall に現れなかった。**

## ⚠ 閾値の前提 — この 0.8037 の大半は「同点の入れ替わり」である

**主計器は集合の重なりを数えるので、入れ替わりの重みを区別できない。**
10 位と 11 位が cos 0.30 と 0.05 で離れていて入れ替わったのと、0.3004 と 0.3001 で
並んでいて入れ替わったのが、同じ overlap になる。0.95 / 0.85 という閾値は暗黙に
**近傍が分離しているコーパス**を前提している。

`v3-tie-diagnostic.json`:

| 測定 | median | p90 / max | |
|---|---:|---:|---|
| native の上位 10 境界のギャップ (`cos@10 - cos@11`) | **0.00394** | p90 0.01274 | 近傍はほぼ同点 |
| 768 が失った類似度 (native 空間で評価) | **0.00445** | max 0.06140 | 取ってくる質はほぼ変わらない |
| 境界ギャップ < 0.01 の passage | | **110/136 (81%)** | |

**集合は入れ替わるが、入れ替わった先は元とほぼ同じ近さにある。** 768 が選んだ
上位 10 件は native 空間で測って中央値 0.0045 しか劣っておらず、これは
native 側の 10 位と 11 位の間隔 (0.0039) と同じ桁である。

**このコーパスが同点だらけなのは素性による** — 136 本のうち 118 本が
同一プロジェクトの `tasks/` 計画文書で、話題も文体も重なっている。実際の Kio
アーカイブはこれより異質な文書の集まりになるはずで、そのぶん近傍は分離し
overlap は上がる方向に動く。**したがって 0.8037 は下振れした推定値として読むべきで、
`< 0.85` という帯の当てはめはこのコーパスでは弱い。**

ただし前述のとおり**結論は変わらない** — 曖昧帯も V3b 送りなので、
補正がどう効いても `≥ 0.95` に届かない限り次は V3b である。

**V3b を読むときの予測**: 失った類似度がこの水準なら、recall@10 の差は
小さく出るはずである。もし V3b が大きな recall 差を出したら、それは MRL 幅ではなく
**別の要因を拾っている**疑いがあるので、先にそちらを疑うこと。

## recall は測れていない (guard が正しく発火した)

`--queries eval/golden-queries-fixture-b.jsonl` を渡したが、24 問すべてが
`answerable: 0` で `measured: false` を返した。理由は計画書の予告どおりで、
golden query の正解 20/24 が `.pdf` / `.docx` を指しており、生のコーパスには
OCR 済み本文が存在しないため。

**スクリプトは低い recall を返さず、測れなかったことと理由を返した。**
これは意図された挙動で、「切り詰めのせいで当たらない」と「そもそも候補に無い」を
同じ低い数字にしない (`v3_mrl.py::recall_at_k` の先頭の足切り)。
V3b は index 済み fixture から取り出した Markdown を `--corpus` に渡す必要がある。

# V3b (2026-08-01) — 24 問 fixture の recall

V3a で測れなかった recall を、OCR 済みの `eval/fixtures/normalized-corpus`
(**1013 passages / persona 20 本すべて**) に対して測った。**追加費用なし** —
OCR 済み本文は支払い済みで repo に入っている。

```bash
python3 eval/v3/v3_mrl.py \
  --corpus eval/fixtures/normalized-corpus \
  --queries eval/golden-queries-fixture-b.jsonl \
  --limit 1013 \
  --out eval/v3/results/v3b-mrl.json
```

`--limit 1013` は必須。既定の 400 では `sorted()` 順に打ち切られて p09〜p20 が
丸ごと落ち、answerable が 24 問中 9 問に下がって guard が発火する。
**1013 は現在の適格 passage 数とちょうど一致する** (計測前に数えて確認した)。

## 測定値

**`recall.measured` = `true` / answerable = 24/24。** 値を読んでよい。

| native 2048 | 0.5417 | 13/24 |

| 近傍一致率 (k=10) | run 1 | run 2 |
|---|---:|---:|

## ⚠ 2 回の実行は「完全一致」しなかった — recall は一致した

ブリーフの規則 4 は完全一致を求めているので、ここは正直に書く。

- **recall は両幅とも完全に一致した。外した query の集合まで同一。**
- **近傍一致率だけがずれた。** ずれ幅は top-1 で 0.000987 = `1013 × 0.000987 ≈ 1`、
  すなわち **1013 passage のうち 1 本**の最近傍が入れ替わった。mean overlap の
  ずれも全 10,130 スロット中 **1 スロット**に相当する。

原因は vLLM のバッチ構成に依存する浮動小数の揺れが**同点を割る**ことだと考えられる。
V3a が測ったとおり、このモデルの近傍は中央値 0.004 程度しか離れていない
(→「閾値の前提」節)。**同点が動いても recall が動かなかったこと自体が、
V3a の「入れ替わりは起きるが取ってくるものの質は変わらない」という所見の裏付け**である。

判断に使う数字 (recall) は再現した。近傍一致率を 3 桁目まで引用するときは
この揺れの幅を超えないこと。

## V8(a) — 対称運用のコスト

`tasks/local-adapter-plan.md` §11 の V8。Qwen3-Embedding 系の標準は query 側にだけ
instruct prefix を付ける非対称運用だが、Kio は `prompt_template_hash` が (T, I) を
1 組しか畳まないので**構造的に採れない**。その損失を測った。

`v3_mrl.py` に `--query-instruction` を足した (passage は素のまま、query にだけ前置)。
送った prefix は `v3b-v8a-mrl.json` の `query_instruction` がそのまま正本:

```
Instruct: Given a search query, retrieve relevant documents that answer the query\nQuery:
```

| 条件 | recall@10 (2048) | recall@10 (**768**) |
|---|---:|---:|
| **対称 (現行)** | 0.5417 | **0.5833** |
| 非対称 (query 側 instruct) | 0.4583 | 0.5417 |
| 差 | **−0.0833** | **−0.0417** |

**非対称運用はこの fixture では改善しなかった。両幅とも悪化している。**

→ **V8 は「書き留めるだけ」で閉じてよい。** query 用 profile を分ける仕様改訂は
**実測上の動機を持たない** — 構造的に採れない運用が、採れたとしても得ではなかった。

ただし n=24 なので 1〜2 問の差はノイズの範囲である。主張は
「非対称が有利だという証拠は出なかった」までで、「非対称は有害である」ではない。

## 判断 — **768 で確定。2048 へは移行しない**

| | |
|---|---|
| recall | **768 が native 2048 を下回らない** (0.5833 vs 0.5417)。切り詰めの代償が測定に現れなかった |
| 移行の代償 | `chunk_vec` の DDL 改訂 + `LOCAL_EMBEDDING_DIMENSIONS` 変更 + `tool_profile_hash` 再凍結 + **全再埋め込み** |
| 差し引き | **より高い代償を払って、より低い実測 recall を買うことになる** |

V3a の予測どおりだった。「768 が失った類似度は中央値 0.00445 で、native 側の
10 位と 11 位の間隔 0.00394 と同じ桁。したがって recall@10 の差は小さく出るはず」
— 実際、差は 1 問で、符号は 768 側に付いた。

**+1 問を「768 のほうが良い」と読まないこと。** n=24 で 1 問は
0.0417 に相当し、ノイズである。正しい読みは
**「MRL 768 が recall を落とすという証拠は出なかった」**であり、
それが移行しない理由として十分である。

### 帰結 — 暫定扱いの解除

- `dimensions = 768` は**確定**。
- `tool_profile_hash` = `sha256:f9f610bb…439a` の**暫定扱いを解除**する
  (`dimensions` が唯一の未確定入力だった)。
- [03 §7](../../../docs/03-data-model.md) を理由とする
  **恒久コーパスの埋め込み禁止は解ける。**
- 定数 2 本は現状のまま動かさない — [`fts.rs`](../../../crates/kio-index/src/fts.rs) の
  `CHUNK_VEC_DIMENSIONS` と
  [`local_embedding.rs`](../../../crates/kio-adapter/src/local_embedding.rs) の
  `LOCAL_EMBEDDING_DIMENSIONS`。

### この測定が答えていないこと

- **絶対 recall 0.58 の是非**は V3 の問いではない。V3 は 2 つの幅の差だけを見ている。
  0.58 が低いと感じるなら、それは chunking / 入力構築 / モデル選定の問題であって
  MRL 幅の問題ではない (両側で相殺されている)。
- **日本語 fixture 1 本での結果**である。裁定 2 (総合性能優先) により
  単一言語を採用条件にしていないので V3 の結論は変わらないが、
  他言語で幅の効果が違う可能性は否定していない。
