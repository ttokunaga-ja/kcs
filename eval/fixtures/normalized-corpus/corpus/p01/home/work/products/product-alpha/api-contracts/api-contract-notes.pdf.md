# 台帳イベント API の確認要点

実装者向け

Orchid Ledger 2026.07 2026 年 7 月

この資料は、Hummingbird Payments の接続先が台帳イベント API を扱う際の確認事項をまとめたものです。正式な公開仕様ではなく、リリース準備中に実装チームが共有する補助資料として使います。

## 状態遷移の扱い

実装と運用の接点



### 6. 実装レビュー

レビューでは、操作キーの生成位置、時刻の扱い、例外応答の一貫性を確認します。ログには必要な追跡情報だけを残し、決済に関係する識別子を不用意に展開しないようにします。変更は小さく分け、再送処理と通常処理を同じテスト観点で確認します。



### 3. 受信から記帳まで

受信時には形式を検証し、必要な情報が不足している場合は再送可能なエラーとして返します。受理後は、内部キューに記録されたことと、台帳への反映が完了したことを別の状態として観測します。利用者向けの応答を急ぐために、内部状態を曖昧にしないことが重要です。



## 1. リクエストの考え方

イベントは、外部リクエストをそのまま保存するのではなく、識別子、受信時刻、金額表現、取引コンテキストを正規化して渡します。受信側は、同じ操作を示すキーが既に存在する場合に、作成処理を繰り返さないことを前提にします。



### 7. リリース当日の連携

Poppy Gateway 側で応答の偏りが見えた場合は、まずリクエストの形式と再送量を確認します。Orchid Ledger 側の照合が遅れている場合は、処理を止めずに観測値と影響範囲を当番へ渡します。両方に兆候がある場合は、1つのインシデント記録に集約します。



### 4. 再送と重複

タイムアウト時は、操作キーを変えずに再送します。キーを毎回作り直すと、通信障害と新規操作を区別できません。重複と判断した応答には、既存レコードへの案内を付け、運用担当が調査できる追跡情報を残します。



## 2. 最低限そろえる項目

|  操作キー | 通信のやり直しを同じ操作として判断するための安定した値。利用者が見える文言とは分けて扱う。  |
| --- | --- |
|  発生時刻 | 受信時刻とは別に保持する。タイムゾーンを省略せず、並び替えの根拠を説明できる形にする。  |
|  照合参照 | 後で外部明細と突き合わせるための参照。自由記述の備考欄に混ぜない。  |

### 5. 例外の分類

- 入力不備: 呼び出し元が修正して再実行する。
- 一時的な受信不可: 同じ操作キーで、間隔を空けて再送する。
- 下流待ち: 受理済みとして扱い、状態照会の導線を案内する。
- 照合差異: Ledger Platform の当番へ参照情報とともに引き継ぐ。
